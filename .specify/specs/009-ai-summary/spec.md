# Feature: AI Summary (Commissioner's Take)

> **Spec ID**: 009
> **Status**: Draft — two phases (season history, league-wide view, memory), owner-approved shape
> **Created**: 2026-10-21
> **Last Updated**: 2026-10-27
> **Version**: 0.27

## Overview

The weekly report (`ff-tracker`) currently renders deterministic facts only. This feature adds an optional, AI-written narrative — a "commissioner's take" — as an additional section inside the existing weekly report, in all five output formats. It is not a new CLI and not a new format.

The narrative is generated text and is labelled as such everywhere it appears. If it cannot be generated, the report ships without it and says so. Nothing in the existing deterministic sections changes.

With the memory store enabled, each published summary is also appended, verbatim, to a season log kept in a secret gist, and that log is handed back to the model as what it published in earlier weeks. Memory adds no second artifact: it is the tool's own reports, kept.

---

## Problem Statement

The weekly report tells a commissioner what happened but not how to talk about it. Writing the weekly blurb by hand is the last manual step before the report goes out, and it is skipped when the week is busy. A generated narrative is worth having even though it is imperfect: the alternatives are a hand-written paragraph or no paragraph at all. The narrative must never be able to stop the report.

Two gaps make the take thinner than it should be. It sees one week: it cannot say a team has climbed from sixth to second since Week 3, that two managers have split six meetings, or that a league's scoring is falling — all of that is already in the games the report loads and is thrown away before the prompt is built. And it starts from nothing every Tuesday, so the running jokes and storylines a commissioner would carry week to week have to be reintroduced each time. The first gap is in the data the narrative is given. The second needs somewhere to keep what the tool published last week.

---

## Done when

`ff-tracker` with the feature enabled renders a labelled AI section whose prose can cite this season's earlier weeks and speak to the whole setup across divisions, and with the memory store also enabled a second run for the same week leaves one memory entry for that week rather than two — while a run where the provider or the store fails still produces the full deterministic report plus a visible notice or warning, exit code 0.

---

## Delivery Phases

This amendment carries two phases. They are specced together, approved together, and delivered and verified separately — each ships on its own and one `git revert` removes it.

**Phase 1 ships first.** Phase 2 is planned and delivered against a merged Phase 1, and nothing in Phase 2 is built on an unmerged Phase 1. A build that contains Phase 2 therefore contains Phase 1, and passes Phase 1's criteria as well; AC-028 is worded so it can be checked in either.

**Phase 1 — derived season history and the league-wide view (FR-011, FR-012).** Both are derived prompt input with no store, which is why they share a phase: a per-league history block, and one cross-division block giving the shared headline something to be about. No new variable, no new call, no storage: both ride `AI_SUMMARY_ENABLED`. Shipped alone, a run is today's run plus a larger prompt and `provenance.history_weeks`. It extends AC-001 and AC-002, re-asserts AC-012's mode coverage in AC-025, and adds AC-024…AC-027. The backward-reference exception the history block makes usable lives in FR-004, not in a requirement of its own.

**Phase 2 — memory store (FR-013, FR-014).** Off by default; off means no store call, no prompt change and output byte-identical to a Phase-1 run. Memory is a log of what the tool already published: one gist, one file, one entry per week holding that week's summary verbatim. Nothing is generated for it, nothing is compacted, and the whole season's archive goes into the prompt. It depends on nothing Phase 1 adds — the archive alone gives continuity — and FR-004 carries the two rules the prompt states about it. It extends AC-001, AC-003, AC-005 and AC-006 — the call counts, the never-printed set and the logging boundary each gain a memory case — and adds AC-028…AC-033, WC-002 and LV-005.

**Neither phase** changes section order, any format's shape, the notice path, or a deterministic value; FR-005 states where they land instead.

## Functional Requirements

### FR-001 — Opt-in generation

- The feature is off unless `AI_SUMMARY_ENABLED` is true. With the feature off there is no HTTP call, no section, no notice, no warning, and the output is unchanged from the current report.
- A configured API key does not turn the feature on.
- The feature covers the weekly report CLI only (`ff-tracker`), in regular, playoff (Weeks 15–16) and championship (Week 17) modes. It does not cover `ff-championship` or `ff-season-recap`.
- When on, the narrative is generated once per report execution, before rendering, and the same narrative is embedded in every format the run produces (single format or `--output-dir`). One run is **at most two attempts, one logical call**, regardless of league count and format count (FR-003).

### FR-002 — Payload

The digest sent to the provider is built from the domain models (`DivisionData`, weekly challenges, season challenges, championship leaderboard where present), not from the JSON formatter's output. It carries, per league:

- league name, team count, current week, and weeks remaining in the regular season (`reg_season_count - current_week`, never below zero). `weeks_remaining` is `null` when either input is unknown: the current week is unknown, or `DivisionData.reg_season_count` is `None` — it is `int | None` on that model already, populated from the ESPN `League` settings;
- standings: rank, team name, owner name, record, points for, points against, and a `playoff_status` field reporting whether the team is **currently inside the top four by record**, with points for as the tiebreaker, using the values `in_playoff_position` or `outside_playoff_position`. The field states a position, not a fate — being outside the top four in Week 6 is not elimination — and the digest states that explicitly in a `standings_note`: *"playoff_status is the current position against the top-four cutoff only; it is not a final outcome."* The note is a requirement, not a convenience, because a live run paraphrased a bare status into "eliminated anyway". The JSON formatter emits the same two values (PR #7 landed in `9ecec3a`), so the two wordings agree and this requirement does not depend on it;
- the week's matchups: both team names, both scores, margin, both projected scores, and each team's `true_projection_diff`. A `WeeklyGameResult` row carries only its own `starter_projected_score` and `true_projection_diff`; the opponent's true diff is read from the mirror row, pairing rows by `team_name`/`opponent_name`, and left out when no mirror row exists. There is no opponent true-diff field to read. The digest states explicitly when a league had no matchups this week;
- the weekly challenges that league won, under the mode rule below;
- the derived season history (FR-011): the weeks played so far, and for every team its rank by week, head-to-head records, current streak, scoring trend, best and worst week, average margin, largest win and largest loss — or `null` when the league has no completed games.

**Mode rule (one rule).** The digest derives the mode locally with the same two expressions the formatters use — `any(d.is_playoff_mode for d in divisions)` and `championship is not None` — and the digest must agree with what the formatters render for the same inputs; AC-012 asserts that agreement. It is a deliberate sixth copy of those two lines, not an extraction: each of the five formatters already computes them independently, and `ReportContext._build_context_from_params` is not reachable from a service. In each mode the digest carries:

- regular season: standings and the 13 weekly challenges, with their winners globally;
- Weeks 15–16 and Week 17: bracket matchups or the championship leaderboard instead of weekly team challenges, the 7 player highlights only, standings where the formatters show them, and the 5 season-challenge leaders marked historical (final at the end of Week 14).

The digest contains no league IDs, no ESPN credentials and no API key.

Across divisions, it also carries the league-wide view of FR-012 — `overall_standings` and `weekly_extremes` — which is the only material in the digest addressed to the whole setup rather than one table.

With memory on, the prompt carries one more block (FR-014 states its contents exactly): the season's archive of published summaries. That block is appended to the system prompt rather than to the digest, so the digest's key set is the same whether memory is on or off.

### FR-003 — Request

- One OpenAI-compatible Chat Completions call to `<AI_SUMMARY_BASE_URL>/chat/completions` with `Authorization: Bearer <AI_SUMMARY_API_KEY>`.
- Memory is written from the narrative this call returns (FR-014): no extra call exists for it and no second model. One run is one logical provider call with memory on or off — at most the two attempts this FR allows below.
- `max_tokens` is sent from `AI_SUMMARY_MAX_TOKENS` (default 8000), never hard-coded. Budget and model belong together: on the real three-league digest of 5,158 prompt tokens, `glm-5.3-flash` at 8000 spent the whole budget on reasoning and returned `content: null` with `finish_reason: length`, which is the FR-006 truncation failure — a provider-side truncation, not a configuration error.
- `reasoning_effort` is sent only when `AI_SUMMARY_REASONING_EFFORT` is set, carrying that value. Unset or empty omits the key entirely; it is never sent as `null` or empty. This is a non-standard OpenAI-compatible extension: an endpoint may ignore it, and ignoring it must not be treated as a failure (measured: `glm-5.3-flash` honours it — 0 reasoning tokens, 10.7 s — while `deepseek-v4.1-flash` gains nothing from it, reasoning rising to 4,912 tokens and running slower).
- The socket read is bounded by `AI_SUMMARY_TIMEOUT` seconds. That is a per-operation bound, not a wall-clock deadline: a provider that trickles bytes can outlive it, and no total time budget is guaranteed, so a pathologically slow provider may exceed the configured value. No streaming.
- The system prompt names the exact league count and lists the league names verbatim, instructing exactly that many `leagues` entries and no others. A live run returned four sections for three leagues, so the count and the names are stated rather than left implicit.
- With memory on, that same prompt carries the archive block (FR-014) and states the two rules FR-004 applies to it — quotation and continuation. Neither is a shape the model must return: memory asks nothing of the response at all.
- **At most one retry, and only for a contract failure** — malformed JSON, wrong shape, a league count or name mismatch, or an empty required field, which are sampling noise. There is no retry for HTTP 4xx/5xx (a 410 will not change), a transport error, a timeout, or `finish_reason == "length"` (the budget is fixed, so a second attempt fails identically at the same cost). A malformed or absent `memory` array is not a contract failure and never spends this retry (FR-004). The retry reuses the same prompt and payload: no prompt mutation, no model change, no budget change between attempts. A second contract failure is the ordinary FR-006 outcome. Worst case is two attempts and roughly two socket-read timeouts.
- The response must parse directly as JSON matching the contract in FR-004. Fenced, prefixed or otherwise non-JSON responses are contract failures, not parsed leniently.

### FR-004 — Narrative contract

Response shape:

```json
{
  "headline": "string",
  "leagues": [
    { "league": "string", "paragraphs": ["string"], "bullets": ["string"] }
  ],
  "season_note": "string"
}
```

- `headline`, every `paragraphs` entry and `season_note` are non-empty strings; `bullets` may be empty.
- Each league entry has at least one paragraph, and every paragraph contains at least one word after trimming — a whitespace-only paragraph is invalid. `"paragraphs": []` is a contract failure.
- League matching is a **total order**, applied once per response:
  1. If every league name matches exactly one entry and every entry matches exactly one league (after `strip().casefold()` equality), map by name. Response order is irrelevant.
  2. Otherwise, if the entry count equals the league count, map by position in digest order, and render every heading from our own league names — never from the response. A stray, renamed or duplicated entry at equal counts lands here and renders. Response order is expected to follow the digest order: (1) does not depend on it and (2) is defined by it.
  3. Otherwise — the counts differ and (1) did not resolve — the response is a contract failure: the section is not rendered, wholly or partially.
- Voice: a commissioner addressing the league — direct, dry, allowed to be wry, no invented statistics and no claims about players or teams absent from the digest. Backward references are the one bounded exception, stated below.
- The section is labelled in every format as AI-generated. It is never presented as fact-checked or as a league record. No requirement verifies that its claims are true; only the shape and league matching are validated.
- The narrative may not be used to compute, alter or replace any deterministic value.

**Backward references — the bounded exception.** History and memory make exactly one exception to "only the names and numbers in the digest", and it is bounded the same way the 60-word floor is: carried by the prompt, deliberately not validated. The floor and the no-invention rule are not exceptions of their own — one is guidance and the other is the rule itself.

- The narrative may cite an earlier week of this season — a team, a week and a figure — when that figure appears in that league's `history` block (FR-011), naming the week it comes from.
- The narrative may quote or continue something it published in an earlier week (FR-014): a running bit, a storyline it set up. The archive is the tool's own prose, so this is continuity, not a second source.
- Bound: at most two backward references per league, and nothing outside the current digest, the history block and the archive. This count is prompt guidance, not a validated cap — the same treatment as the 60-word floor. Nothing counts citations, and no acceptance criterion asserts the count.
- The no-invention rule is unchanged and applies to backward references: a figure that is in neither the digest nor the history block is invented, whether or not an earlier summary implies it.
- Nothing here is verified. There is no parser, counter or post-generation check: the rule is carried by the prompt and the label, exactly as the no-invention rule is.

**The archive in the prompt (memory on only).** The block is a transcript of this tool's own reports (FR-014), and the system prompt states exactly two rules about it:

1. **Quotation.** The archive is *what you published in earlier weeks* — a record of its own reports, never a source of league fact. This week's data is the truth; where the two disagree, the current data wins and the older line may only be quoted as something it said.
2. **Continue, don't repeat.** A running bit escalates or retires. Repeating a joke in the same words is the failure this memory exists to prevent.

Neither rule is validated, exactly as the no-invention rule is not, and neither asks anything of the response: memory authors no field.

**Length caps, enforced after the contract checks:** `headline` ≤ 15 words; per league ≤ 3 paragraphs, ≤ 3 bullets, and ≤ 120 words across its paragraphs (bullets count only against the ≤ 3 bullet cap, not against the 120 words); `season_note` ≤ 40 words.

**Validation order, fixed:** contract shape → league matching (the total order above) → length normalisation → render. Normalisation is deterministic and total — the same response normalises to the same output every time — and it never turns a valid response into a contract failure. The archive is outside this order entirely: it is prompt input, and nothing in the response depends on it.

**Normalisation, in this order:**

1. Drop bullets after the third, in response order.
2. Drop paragraphs after the third, in response order.
3. If a league's paragraphs still exceed 120 words, drop whole trailing paragraphs until they fit. If the **first** paragraph alone exceeds 120 words, truncate it at the last word boundary at or before 120 and append `…`, dropping every other paragraph.
4. Truncate `headline` beyond 15 words at a word boundary with `…`. Truncate `season_note` beyond 40 words at a word boundary with `…`.

There is no sentence detection anywhere in this path: initials in names (`J.J. Smith`, `A.J. Brown`) are indistinguishable from sentence ends, so the rule is structural — whole bullets, whole paragraphs, then whole words. `…` is appended only where step 3 or 4 cut a first paragraph, the headline or the season note.

120 is a cap, not a target: the 60-word floor is prompt guidance only, deliberately not validated, because enforcing it would mean padding the prose — inventing facts — or dropping a short section, both worse than a short take.

`provenance.truncated` is `true` when normalisation dropped or shortened anything for this report, and absent or `false` otherwise.

### FR-005 — Rendering

The section appears **after the weekly highlights and before the season-long challenges**, in every format that has a position; JSON keeps `ai_summary` as a top-level key and does not move. Report order in the positioned formats: `header → weekly highlights → Commissioner's Take → season-long challenges → per-league standings → overall top teams → game data`. No existing section changes its content or its order relative to the others.

**Season history and memory touch none of this.** Both are prompt input: the section's position, its heading, its per-format shape, the notice path and every deterministic section are exactly as in the table below whether history and memory are absent, present, or failing. The only output-visible effect of either phase is four JSON `provenance` fields in FR-008 — `history_weeks` from Phase 1, and `memory_read`, `memory_write` and `memory_weeks` from Phase 2 — and nothing else; all four appear only when a narrative renders, so the notice path carries none of them. The AC-001 and AC-018 assertions stand unmodified. If a later plan proposes rendering a history table or a "what I said last week" line, that is a new requirement, not an implementation detail of this one.

| Format | Placement | Shape | Absent |
|---|---|---|---|
| console | after the weekly highlights table, before the season-long challenges | `🤖 COMMISSIONER'S TAKE (AI-GENERATED)` header, headline, per-league subsection, paragraphs, `•` bullets, `Generated by <model> · AI-generated text` line | one-line notice in the same position |
| sheets | after the weekly challenge rows, before the season-challenge rows | `AI SUMMARY (AI-GENERATED)` row, `HEADLINE:` row, `LEAGUE:` row per league, paragraphs flattened to one row each, bullets as `- ` rows, attribution row | one-line notice row |
| email | after the weekly highlight sections, before the season challenges and standings | section with heading, AI-generated marker, `<p>` paragraphs, `<ul>` bullets, attribution line; HTML-escaped; team names inside the text wrapped in `<span class="ai-team">`, with the `.ai-team` rule in the email's stylesheet setting the weight and the `email.ai_team_color` colour (default `#0b57d0`) | one-line notice |
| json | top-level `ai_summary` key, unchanged | object described below | `"ai_summary": {"error": "<notice text>"}` |
| markdown | after the weekly highlight sections, before the season challenges and standings | `## 🤖 Commissioner's Take (AI-generated)`, `### <league>`, paragraphs, `- ` bullets, italic attribution line | one-line notice |

**Email team-name highlighting (email format only).**

- Every occurrence of a team name that appears in the report data is wrapped in `<span class="ai-team">` — in the headline, paragraphs, bullets and season note. Matching is case-insensitive and the text is kept exactly as the model wrote it, so the span preserves the original casing.
- Longest name first, so a name that is a prefix of another does not win, and names match as whole names rather than as fragments of other words.
- Wrapping does not weaken escaping: each segment is HTML-escaped, so a name containing an apostrophe (`Drew's Daring Team`, `I don't consent`) and any `<`, `>`, `&` in the prose render as text, never as markup. A narrative with no team name is escaped exactly as today.
- The span carries only `class="ai-team"` — no `style` attribute — and the email's stylesheet owns the appearance: `.ai-team { color: #0b57d0; font-weight: 700; }`, with the `email.ai_team_color` value in place of `#0b57d0`. This matches the rest of the template, where `.winner`, `.challenge-name`, `.playoff-team` and `.container` also carry their declarations on the class, and it is what lets `email.ai_team_color` style the highlight by class. The trade-off, stated rather than hidden: a client that strips `<style>` loses the highlight, exactly as it already loses those other classes.
- The `.ai-team` rule is emitted only when a narrative renders: never on the notice path and never when the feature is off.
- The notice path (`AISummaryUnavailable`) is unaffected: no wrapping, no spans. Console, markdown, sheets and JSON are unchanged.

JSON `ai_summary` object:

```json
{
  "headline": "string",
  "season_note": "string",
  "leagues": [{ "league": "string", "paragraphs": ["string"], "bullets": ["string"] }],
  "provenance": { "model": "deepseek-v4.1-flash", "prompt_sha": "9f2c1ab4e7d0", "generated_at": "2026-10-14T05:03:11Z", "truncated": false, "attempts": 1, "history_weeks": 6, "memory_read": "ok", "memory_write": "ok", "memory_weeks": [1, 2, 3, 4, 5, 6] }
}
```

- `ai_summary` is absent when the feature is off; present (narrative or error) when it is on.
- **Provenance exists only where a narrative does.** All four of `history_weeks`, `memory_read`, `memory_write` and `memory_weeks` are present only when a narrative rendered; the notice path carries none of them, because `ai_summary` is then `{"error": "…"}` with no `provenance` object at all — today's behaviour and the intended one.
- `provenance.history_weeks` is the number of distinct weeks in the digest's history blocks, counted as a union across leagues; `0` when no league has a completed game.
- `provenance.memory_read`, `provenance.memory_write` and `provenance.memory_weeks` are present when memory is on, and absent when it is off, so a Phase-2 run with memory off produces the same JSON as a Phase-1 run.
- `memory_read` is `"ok" | "none" | "failed"` and `memory_write` is `"ok" | "failed" | "skipped"`; FR-014 owns the map that decides each value. `memory_weeks` is the list of week numbers that were in the prompt — `[]` when none were — so a report says exactly what the model was shown rather than only that the store answered. The two read statuses are what separate "never configured, or nothing published yet" from "the store has been rejecting this run's token for the whole season", which a single boolean could not.
- Cell values in sheets and console must not contain tabs or newlines; paragraph text is flattened, not reflowed or summarised.

### FR-006 — Failure policy: the report always ships

Any failure while obtaining, matching, validating or normalising the narrative produces the same result: the deterministic report is rendered and written as normal, the section is omitted, the run exits 0, and the failure is visible in two places:

1. a one-line notice in the output, in the section's position — after the weekly highlights, before the season-long challenges — in the format's own style: `AI summary unavailable: <reason>. The report is unaffected.` In JSON the notice is the value of `ai_summary.error`. The notice stays where the section would have been — it is not hoisted into the header, because nothing about the deterministic report changed.
2. when `GITHUB_ACTIONS` is `true`, a workflow command on stdout: `::warning::AI summary unavailable: <reason>.` — outside Actions no workflow command is emitted, so console output stays clean. This warning is the visibility backstop that a bottom-of-report notice needs.

`<reason>` names what failed and never includes the API key or the response body: for HTTP errors `HTTP 410 (model glm-5.3-flash at opencode.ai)`; for transport errors `connection failed (opencode.ai)`; for timeouts `timed out after 120s`; for truncation `finish_reason=length`; for shape problems `response did not match the summary contract`; for a league-count mismatch `league count mismatch (3 leagues, 2 sections)`. The endpoint appears as its **host only**, never its path or query, because a custom base URL may embed a credential there — with a defaulted endpoint, the host is also what tells a commissioner whether the default or their override failed.

The memory store has its own cases, in the same posture, and **none of them produces this notice**: FR-014's status map owns them. A read never changes the report, the section or the narrative — the take is generated without the archive — and no read failure puts a notice, a line or a marker in any format; the only signal a read failure has is the one FR-014 assigns it, silence for `"none"` and for a 5xx, transport error or timeout, and exactly one `::warning::` under Actions for a 401/403, which is the one failure an operator can fix and otherwise the one that can go unnoticed for a season. A write failure ships the report, records `provenance.memory_write: "failed"`, and emits exactly one `::warning::` under Actions and none otherwise, exit 0 — a warning, not a notice, because the section was produced and the notice slot is for a section that is not there. No memory outcome can stop a run.

This is a deliberate, documented exception to Article III (see Constitution Deviations).

### FR-007 — Enabled but not configured

Configuration errors are not narrative failures and are not degraded. Every bullet below applies only when `AI_SUMMARY_ENABLED` is true, with one exception — a malformed `AI_SUMMARY_ENABLED` is itself an error, because an unreadable flag cannot be read as off. A malformed value of any other `AI_SUMMARY_*` variable is ignored while the feature is off: the feature must not be able to change the report's behaviour when it is off.

- `AI_SUMMARY_ENABLED` true with `AI_SUMMARY_API_KEY` missing or empty → `ConfigurationError` naming `AI_SUMMARY_API_KEY`, exit 1, no report, no HTTP call.
- `AI_SUMMARY_ENABLED` set to any value not in `true|1|yes|on|false|0|no|off` (case-insensitive) → `ConfigurationError`.
- `AI_SUMMARY_TIMEOUT` not a positive integer → `ConfigurationError`.
- `AI_SUMMARY_MAX_TOKENS` not a positive integer → `ConfigurationError` naming the variable.
- `AI_SUMMARY_REASONING_EFFORT` set to anything outside `low|medium|high` (case-insensitive) → `ConfigurationError` naming the variable and the allowed values.
- `AI_SUMMARY_MAX_PROMPT_CHARS` not a positive integer → `ConfigurationError` naming the variable.
- `AI_SUMMARY_USER_PROMPT` longer than `AI_SUMMARY_MAX_PROMPT_CHARS` → `ConfigurationError` naming the variable, its actual length and the configured limit.
- With memory on (FR-013): `AI_MEMORY_GIST_ID` or `AI_MEMORY_GIST_TOKEN` missing or empty → `ConfigurationError` naming that variable, exit 1, no report, no provider call and no store call. `AI_MEMORY_ENABLED` set to a value outside the same eight values → `ConfigurationError`.
- The `AI_MEMORY_*` group is validated only when `AI_SUMMARY_ENABLED` is also true. Memory changes the prompt only, so with the feature off memory is inert: no store call, and a malformed memory variable cannot deny a report it has no effect on.
- A **blank** value of any optional variable means "use the default", not "malformed": `AI_SUMMARY_TIMEOUT=` gives 120, `AI_SUMMARY_MAX_TOKENS=` gives 8000, `AI_SUMMARY_MODEL=` gives the default model. A malformed **non-blank** value is still a `ConfigurationError`. The memory settings have no defaults — a blank gist id or token is the missing-value error above, not a fallback.
- Misspelled or missing provider settings therefore fail loudly once, instead of quietly degrading every scheduled run.
- Because that failure produces no report, the weekly workflow sets `AI_SUMMARY_ENABLED=true` only when `secrets.AI_SUMMARY_API_KEY` is non-empty, and omits it otherwise. The base URL needs no guard because it has a default. The guard is an `env:` expression yielding the literal `true`/`false` (e.g. `AI_SUMMARY_ENABLED: ${{ secrets.AI_SUMMARY_API_KEY != '' }}`) consumed by the step that writes `.env`. It cannot be an `if:` condition: `secrets` is not available in `jobs.<job_id>.if` or `steps.<job_id>.if`, so such a condition evaluates without the secret and silently disables the feature. No workflow sets the flag unconditionally.
- The memory flag is guarded the same way, for the same reason: `AI_MEMORY_ENABLED` is `true` only when the gist id and token are both present — `${{ secrets.AI_MEMORY_GIST_TOKEN != '' && vars.AI_MEMORY_GIST_ID != '' }}` — so a checkout without them ships a normal report instead of failing on a required memory setting (FR-013, WC-002).

**Tradeoff, stated plainly:** a fork or a rotated credential leaves the flag on with no key, and with the flag on that means no report at all — not a report without a narrative. Without the workflow guard, a missing secret would silently stop the weekly report, which is the one outcome this feature must not cause. With the guard, a checkout without the key produces a normal report with the feature off, and gets no AI section until an operator supplies the key. The guard is therefore a requirement, not workflow polish. Memory is different in exactly one respect: a **present but revoked** gist token is not a configuration error, because a value that exists cannot be told from a working one before it is used. The store answers 401/403, and FR-014 records that as a failed read or write.

### FR-008 — Provenance and determinism

- JSON records `provenance.model`, `provenance.prompt_sha`, `provenance.generated_at` (ISO 8601 UTC), `provenance.truncated` and `provenance.attempts` (1 or 2, so a report shows whether a retry was needed).
- `prompt_sha` hashes the **instructions only**: the system-prompt template, the league scope of FR-003, and the `### COMMISSIONER'S INSTRUCTIONS` block when `AI_SUMMARY_USER_PROMPT` is set (FR-010). That is byte-for-byte the definition every report archived so far was produced under, so those hashes stay comparable. The memory block is deliberately outside it: a value that changes every week would make `prompt_sha` incomparable across weeks and stop it saying the one thing it is read for — that the instructions did not change.
- `provenance.memory_weeks` is the list of week numbers that were in the prompt, defined in FR-005; it is present when memory is on and is `[]` when nothing was shown.
- The limitation stated plainly: the user prompt is not in git and the archive is not archived with the report, so an archived CI report shows that the same instructions (`prompt_sha`) and the same weeks of context (`memory_weeks`) produced it but cannot reproduce either — retaining them is the operator's responsibility, and the gist is the archive's only record. A local `-vv` run can reconstruct the template and the league scope (FR-009); an archived CI report cannot, and logging is not a substitute for retaining the value.
- `provenance.history_weeks`, `provenance.memory_read`, `provenance.memory_write` and `provenance.memory_weeks` are defined in FR-005: all four when a narrative renders, with `history_weeks` from Phase 1 and the other three from Phase 2, and none of them on the notice path.
- console, sheets, email and markdown carry the model id in the attribution line. They do not carry `prompt_sha`.
- The narrative is not deterministic: two runs over identical data may differ in wording and emphasis, and no requirement compares two live generations.
- For identical inputs and identical narrative outcome, every deterministic section is byte-identical, and is identical to a run with the feature off. The report's facts never depend on the narrative.

### FR-009 — Secrets and privacy

- The API key — and, once memory is on, the gist token (FR-013) — never appears in any output, artifact, error message, notice, warning command or log line, including when the provider echoes it back in an error body or header.
- The key is supplied only through `AI_SUMMARY_API_KEY` (environment or `.env`, same loading as `ESPN_S2`/`SWID`). There is no CLI flag and no `--format-arg` for it — format arguments are for presentation and must not carry credentials. The gist token follows the same rule through `AI_MEMORY_GIST_TOKEN`, and is the only credential the store call carries.
- **Never logged at any level** — INFO, DEBUG, error messages, notices or warning commands: the API key, the gist token, the request body (the digest, which carries team names, owner names, and points for and against), the response body, and the memory text read from the store. Only the model, HTTP status, latency and token counts may be logged.
- **Logged at DEBUG only:** the system prompt — the template, the resolved `### COMMISSIONER'S INSTRUCTIONS` block (FR-010), the league scope it states (the league count and the league names) and, with memory on, the archive block **with its text replaced**. The memory half is a requirement on the line's content, not a description of it: the line is the composed system prompt except that each stored entry's prose is replaced by its week tag, so the block's shape is visible and its paragraphs are not — the archive is prose about teams and the block is part of the system prompt. Of the report's data, only **league names** may appear, and only in that line: no team names, owner names, scores, projections or any other digest content, at any level. It is never logged at INFO, WARNING or ERROR, and never appears in an error message, notice or warning command.
- Why the split matters: this repository is public and GitHub Actions logs are world-readable, so that DEBUG line is for a local `-vv` run — do not enable verbose logging in CI. For CI the record is the `AI_SUMMARY_USER_PROMPT` variable or secret itself (FR-008); logging is not a substitute for it.
- Team names, owner names and scores leave the machine and are sent to `AI_SUMMARY_BASE_URL`. `AI_SUMMARY_USER_PROMPT` (FR-010) is sent verbatim to the provider, so it must never contain credentials. The prompt is supplied by a repository **variable**, by a **secret**, or by a one-run `workflow_dispatch` input (FR-010), in that order of preference: repository variables are not masked in logs, whereas secrets are, so a prompt that must never be published belongs in the secret; a dispatch input appears in the run's inputs and belongs to no one who needs a secret. `ff-tracker --help` states this under the feature's configuration section.

### FR-010 — User prompt

- `AI_SUMMARY_USER_PROMPT` is optional and defaults to empty. It is free-form — tone, nicknames, running jokes, facts to mention, things never to say — with no required structure. It is appended to the system prompt as a clearly delimited block: `### COMMISSIONER'S INSTRUCTIONS` on its own line, then the value, sent verbatim inside that block.
- **Sources, highest precedence first:** the `ai_summary_prompt` `workflow_dispatch` input for that run, then the repository variable `AI_SUMMARY_USER_PROMPT`, then the secret of the same name, then empty. The input applies to that run only and does not persist; an empty input falls through to the variable or the secret rather than clearing them. Dispatch string inputs are single-line, so a multi-line standing prompt belongs in the variable or the secret. The value is sent to the provider, and when it comes from the input it also appears in the run's inputs — so never put a secret in a dispatch input.
- Reading rules: the value is used exactly as supplied; leading and trailing whitespace is stripped and internal newlines are preserved; CRLF is normalised to LF. An empty or whitespace-only value means "no extra instructions" and is not an error — the block is then omitted rather than sent empty.
- Size cap: `AI_SUMMARY_MAX_PROMPT_CHARS` characters (default 8000), measured after the whitespace strip. Exceeding it is a `ConfigurationError` naming the variable, the actual length and the configured limit — never a hard-coded number. The default bounds prompt size and cost rather than a platform: Linux permits roughly 128 KB per environment variable and GitHub caps a secret at 48 KB.
- **Precedence:** the user prompt shapes tone and content only, and is ignored wherever it would contradict the JSON contract, the caps and normalisation (FR-004), or the "no invented facts" rule (FR-004).
- The user prompt is trusted input authored by the commissioner and is not sanitised: the JSON contract and normalisation run after generation and are the actual guardrail. Nothing in this feature validates the factual accuracy of the prose, including anything the user prompt asks it to say.
- It is never echoed into the report; `prompt_sha` (FR-008) is the only trace of it.

### FR-011 — Derived season history (Phase 1)

The narrative can only talk about the season if the prompt contains the season. The digest gains a `history` block per league, computed from exactly the games the report already holds — `DivisionData.games`, the same collection the season challenges are computed from. No new ESPN field, no additional API call, no storage, no configuration: it is computed once per run when `AI_SUMMARY_ENABLED` is true and is never persisted.

The block:

| Field | Type | Meaning |
|---|---|---|
| `weeks_included` | list of int | the weeks with at least one game, ascending |
| `teams[].team` | str | team name |
| `teams[].rank_by_week` | list of `{week, rank}` | that team's standings rank at the end of each week present; the latest week present is taken from the digest's `standings[].rank` verbatim, earlier weeks are recomputed |
| `teams[].head_to_head` | list of `{opponent, wins, losses}` | one row per opponent met |
| `teams[].streak` | `{kind: "win"\|"loss", length}` or null | the run still standing at the latest week present; `null` when the team has no game in the collection |
| `teams[].scoring_trend` | `"up"\|"down"\|"flat"\|null` | latest week's score against that team's mean over the earlier weeks present: `up` or `down` beyond 1.0 point, otherwise `flat`; `null` when fewer than two weeks are present |
| `teams[].best_week` / `teams[].worst_week` | `{week, score}` or null | highest and lowest single-week score; `null` when the team has no game in the collection |
| `teams[].average_margin` | float or null | mean of `score - opponent_score` over that team's games: signed, so a loss is negative; `null` when the team has no game in the collection |
| `teams[].largest_win` / `teams[].largest_loss` | float or null | the largest amount the team won by and the largest it lost by, as magnitudes like `GameResult.margin`; `null` when the team has not won or not lost |

- Rank at week N is the order the standings already use — wins descending, then points for descending — computed over each team's games with `week <= N`. A tie is broken by that same order; nothing new is invented. **The latest week present is the anchor and the exception:** its ranks are the digest's own `standings[].rank` values, taken verbatim, so the newest column always agrees with the standings the narrative also reads. The anchor holds even when `DivisionData.games` is missing a week the standings still count — a tolerant collection can disagree with `TeamStats`, and the newest column is the one that must not.
- `scoring_trend` compares one number against one number and nothing else: `up` when the latest week's score exceeds the mean of the earlier weeks present by more than 1.0 point, `down` when it is below by more than 1.0, `flat` otherwise, and `null` when fewer than two weeks are present — a single week asserts no trend.
- `history` is `null` when the league has no games, and the system prompt states that `null` means no completed games, so no pattern may be asserted from it.
- **A team with no game in the collection** — possible because `DivisionData.games` is built tolerantly — has `streak`, `best_week`, `worst_week` and `average_margin` as `null`, an empty `rank_by_week` beyond the anchor week and an empty `head_to_head`. It is still listed in `teams`, because the roster is the roster; it simply has nothing derivable, and the prompt says a `null` figure may not be cited.
- Which weeks are present is whatever `DivisionData.games` holds. History adds no rule about playoff weeks and fetches nothing extra; a week the report does not have is not in the block and may not be cited (FR-004's backward-reference exception).
- History is prompt input only: no format gains a section, a field or a line, and no existing section changes (FR-005).
- History has no switch of its own. It rides `AI_SUMMARY_ENABLED` and is on whenever the feature is on, in regular, playoff and championship modes alike.

### FR-012 — League-wide view (Phase 1)

One league of 24-plus people had to be split across divisions for platform reasons, and the shared headline is the only part of the summary addressed to everyone at once. Today it has nothing cross-division to be about: the digest is per-division, so the narrative can only eyeball three separate tables. This block gives it material, and like FR-011 it is derived from data the report already holds — no new ESPN field, no additional call, no storage, no configuration, riding `AI_SUMMARY_ENABLED`.

| Field | Shape | Meaning |
|---|---|---|
| `overall_standings` | list of `{rank, team, division, record, points_for}` | every team in every division in one ranking |
| `weekly_extremes` | `{highest_score, lowest_score, biggest_win, closest_game}` or `null` | this week measured across every division |

- **`overall_standings` orders exactly as the report's overall table already does** — the teams of all divisions sorted by wins descending, then points for descending (`base.py:_get_overall_top_teams`), rank 1 being the first row. The digest states that rule rather than inventing a second one, and where the console table stops at 20 the digest carries **every** team, because the jokes land at the bottom as often as at the top. The digest's ranking must agree with the console's overall table for the same inputs — the same agreement FR-002 already demands of the mode rule, and for the same reason: two orderings of one dataset that drift apart are a lie in whichever one is read second.
- Each row names the team's division, so a cross-division claim can say which table a team came from.
- **`weekly_extremes` is measured across all divisions, not within one.** `highest_score` and `lowest_score` are `{team, division, score}`; `biggest_win` and `closest_game` are `{team, division, opponent, margin}`. It is computed from the weekly matchups the digest already carries, across every division — new computation over loaded data, not a new fetch — and where one of those values coincides with a per-division weekly challenge winner the two must agree, because both read the same rows.
- `weekly_extremes` is `null` when the run has no weekly matchups to measure: Week 1 before kickoff, or a mode whose digest carries none (FR-002). In a playoff or championship week with a season behind it, `overall_standings` is still present — the standings exist.
- **One division only:** `overall_standings` still exists and equals that division's standings, and `weekly_extremes` still exists. Nothing here is conditional on there being more than one division.
- **A league with no completed games at all:** both are `null`, and the system prompt says so, exactly as FR-011 requires of `history`. A table of every team at 0-0 is not a ranking, so nothing is sent rather than something misleading.
- **Prompt rules, two.** An overall claim may only come from this block — a division's `rank` is a division rank, and the narrative may not describe a per-division `rank: 1` as the best record in the whole setup. And this block is the source for cross-division statements (best team, worst team, the week's biggest blowup across everyone), while nothing about it changes a per-division value.
- **No rendering.** No format gains a section, line or field, and no provenance field is added, so FR-005's "only output-visible effect" sentence stays true for this block.

### FR-013 — Memory store (Phase 2)

- Off unless `AI_MEMORY_ENABLED` is true. Off means no store call, no archive block in the prompt, no memory fields in provenance, and output byte-identical to the same run before this phase existed. Memory also requires `AI_SUMMARY_ENABLED`: with the feature off, memory is inert — no store call, and no configuration error from a memory variable (FR-007).
- **One secret GitHub gist, one file, named `memory.json`.** One gist is one commissioner setup — their 24-plus people across divisions — and that is the whole key: the gist identifies the league group, so no league id appears in a file name and no aliasing is needed anywhere in the prompt. A second group is a second gist, not a second directory.
- **Stated plainly, not glossed: GitHub has no private gist.** A secret gist is *unlisted*, not private — anyone who obtains its URL can read it, and the tool must assume exactly that. The owner accepted this. What it holds is bounded by FR-014: this tool's own published prose and week tags, never the digest, standings, scores, projections, the prompt, the API key or any credential.
- Credentials: `AI_MEMORY_GIST_ID` and `AI_MEMORY_GIST_TOKEN` — a fine-grained token with Gists read and write, or a classic token with the `gist` scope. Both are required when memory is on (FR-007).
- Traffic: at most **one read, and one write only when that read succeeded**, per run, regardless of league count — the discipline FR-001 applies to the provider call and Article V applies to ESPN. The store client's socket read is bounded by `AI_SUMMARY_TIMEOUT`, so no new timeout setting is added.
- Standard library only (`urllib`, `json`), with the transport injectable exactly as the provider client's is, so tests use a fake store and need no network. No new runtime dependency.
- The gist id and the token never appear in any output, artifact, error message, notice, warning or log line (FR-009).
- The weekly workflow forwards the three settings the way FR-007's are forwarded — the token from a secret, the id from a repository variable — guarded so a checkout without them ships a normal report (WC-002). A missing or empty gist id or token while memory is on is a `ConfigurationError` naming the variable, exit 1, no report, no provider call and no store call, as FR-007 already requires of every memory setting.
- Covers the weekly report CLI only, as FR-001.

### FR-014 — Memory record and lifecycle

The file:

```json
{
  "schema": 1,
  "season": 2026,
  "entries": [
    {
      "week": 6,
      "generated_at": "2026-10-14T05:03:11Z",
      "headline": "string",
      "season_note": "string",
      "leagues": [
        { "league": "string", "paragraphs": ["string"], "bullets": ["string"] }
      ]
    }
  ]
}
```

- **An entry is the published summary verbatim plus a week tag.** `week`, `generated_at`, `headline`, `season_note`, and `leagues` holding every league's paragraphs and bullets exactly as the report rendered them. Nothing is distilled, summarised, paraphrased or asked of the model for it: memory is a log of what was published, not a second artifact in a second voice.
- **`schema` is `1`, and `season` records the season** for legibility. Every entry in a file belongs to that season; memory does not span seasons, and nothing in this feature rolls a file over, compacts it or carries it forward. **Entries are keyed by week inside a file whose `season` is fixed when the file is created**, so a run in a later season would replace the same week's entry rather than add to it: the operator retires `memory.json` at a season boundary — a new gist, or an emptied file — and that is a documented consequence of the single-season assumption, not behaviour this feature performs.
- **Append-only at the run level.** One read before generation and one write after the narrative is accepted. Nothing written earlier is ever modified, reordered or dropped — which is what makes a hand edit inside an earlier entry safe by construction. There is no authorship marker, because append-only makes one unnecessary.
- **A re-run of the same week replaces that entry.** A dispatch re-run must not stack a second take for the same week, so the entry whose `week` equals the report's week is replaced in place. That is the only mutation in the whole feature, and the only removal.
- **The whole archive goes into the prompt.** The `### MEMORY` block carries every entry in the file, in week order, each under its week tag, introduced as *what you published in earlier weeks*. No selection, no window, no truncation, no dropping, no caps on the text: a hand-edited entry is sent exactly as written. FR-004 states the two rules the prompt gives about it.
- **Read outcomes.** `provenance.memory_read` reports the run's single read:
  - an absent file, or an empty gist, is `"none"`: nothing published yet, no warning, and the write is still attempted once the narrative exists;
  - a **404** is `"none"`: the gist or the file is not there yet, no warning, and the write is still attempted — which then 404s in turn and is AC-032's write failure.
  - a 401/403 is `"failed"`, with exactly one `::warning::` under `GITHUB_ACTIONS` naming it an authentication failure — the one failure an operator can fix, and the one that would otherwise stay invisible for a whole season;
  - a 5xx, a transport error or a timeout is `"failed"`, recorded and silent: no notice, no `::warning::`.
  - `"ok"` means the file was read with at least one entry in it. On any failure the narrative is generated without the archive, and **no read failure ever appears in the report** — not as a notice, not as a line, not as a marker in any format.
- **A failed read suppresses the write.** The write is skipped when the read failed for any reason — auth, server, transport, timeout, or an unparseable file — as well as by the season/week guard below: the merge cannot preserve what it never read. Writing anyway would replace a whole season with a single entry, silently, because read failures are the silent kind; a transient GitHub 500 must cost one week of memory, not the season. After a failed read the store is left exactly as it was, and `provenance.memory_write` is `"skipped"` — never a later `"ok"` or `"failed"` for that run.
- **Write outcomes.** `"ok"` when the entry was written; `"failed"` on a 404 (the gist is gone), a 401/403, a 5xx, a transport error or a timeout — the report ships complete, exit is 0, and exactly one `::warning::` is emitted under `GITHUB_ACTIONS` and none otherwise, naming scope or authentication wherever that is identifiable; `"skipped"` when no write was attempted, which is a failed read, a failed narrative, or a run whose season is not a four-digit year or whose week is not an integer 1–18.
- **The season and week guard** is the other condition that can suppress a write. A pre-kickoff run has `espn_service.current_week` at 0 or negative, and an entry cannot be keyed by a week that is not in 1–18; skipping keeps such a run from writing an entry nothing can ever address. Nothing else about the file's content gates anything.
- **A file that does not parse as the archive shape** is treated as no memory for that run, is **not** overwritten, and warns once under `GITHUB_ACTIONS`. "Parses as the archive shape" means: valid JSON, `schema` is the supported value, the required keys are present, and every `week` is an integer in 1–18. Nothing else is checked — content, entry counts, text length and season agreement never make a file read-only — so a hand-edited file with extra fields or long paragraphs is read and sent as written, while a genuinely malformed one degrades instead of crashing the run.
- **Provenance.** `provenance.memory_read` (`"ok" | "none" | "failed"`), `provenance.memory_write` (`"ok" | "failed" | "skipped"`) and `provenance.memory_weeks` (the weeks that were in the prompt, `[]` when none were) exist only when memory is on — absent when it is off (FR-005, FR-008).
- **Size, stated once and plainly.** One week's entry is roughly 500 words across three leagues, so by Week 17 a league group's file is about 56 KB on disk and about 10,000 prompt tokens. That is the whole cost, and it is not a reason to shorten anything: at typical input pricing a whole season's archive costs a few cents, and nothing in this feature caps, prunes or budgets it. What bounds the reply is `AI_SUMMARY_MAX_TOKENS`, which is the *reply* budget and has nothing to do with the prompt's size.
- Nothing in this path can stop the report or change the narrative: no memory failure produces the FR-006 notice, because the section was produced. This is the second and third case of Article III's declared exception.

## Configuration

| Variable | Required | Default | Meaning |
|---|---|---|---|
| `AI_SUMMARY_ENABLED` | no | `false` | Opt-in switch. Off means no call, no section, no notice. |
| `AI_SUMMARY_API_KEY` | when enabled | none | Bearer token; never printed. |
| `AI_SUMMARY_BASE_URL` | no | `https://opencode.ai/inference/openai/v1` | OpenAI-compatible endpoint root; `/chat/completions` is appended. An empty or whitespace-only value falls back to the default rather than erroring. |
| `AI_SUMMARY_MODEL` | no | `deepseek-v4.1-flash` | Model id, reported verbatim in errors and provenance. |
| `AI_SUMMARY_TIMEOUT` | no | `120` | Per-socket-read timeout in seconds. There is no wall-clock deadline, so a slow provider can exceed it. |
| `AI_SUMMARY_MAX_TOKENS` | no | `8000` | Positive integer sent as the request's `max_tokens`. It bounds the **reply**, not the prompt, so it has no bearing on how much memory is sent. Too small a budget for the chosen model shows up as an FR-006 truncation failure. |
| `AI_SUMMARY_REASONING_EFFORT` | no | unset | Optional `low|medium|high` (case-insensitive). When set, the request carries `reasoning_effort: <value>`; when unset or empty, the key is omitted entirely. A non-standard extension an endpoint may ignore, which is not a failure. |
| `AI_SUMMARY_MAX_PROMPT_CHARS` | no | `8000` | Positive integer bounding `AI_SUMMARY_USER_PROMPT`; a cost guard, not a platform limit — Linux allows roughly 128 KB per variable and GitHub caps a secret at 48 KB. |
| `AI_SUMMARY_USER_PROMPT` | no | empty | Free-form commissioner instructions appended to the system prompt (FR-010); stripped, CRLF-normalised, bounded by `AI_SUMMARY_MAX_PROMPT_CHARS`. |
| `AI_MEMORY_ENABLED` | no | `false` | Phase 2 opt-in. Off means no store call, no memory block, no memory provenance fields. Inert while `AI_SUMMARY_ENABLED` is off. |
| `AI_MEMORY_GIST_ID` | when memory is on | none | Id of the secret gist holding the single `memory.json` (FR-013). |
| `AI_MEMORY_GIST_TOKEN` | when memory is on | none | Token with Gists read+write; never printed, never logged. |

These are loaded the same way as existing settings (`load_environment` / `.env`); the weekly workflow forwards the optional AI settings from repository variables, and takes `AI_SUMMARY_USER_PROMPT` from the one-run `ai_summary_prompt` dispatch input, then `vars.AI_SUMMARY_USER_PROMPT`, then `secrets.AI_SUMMARY_USER_PROMPT`, then empty (FR-010). The memory settings follow the same pattern — `AI_MEMORY_GIST_ID` from a repository variable, `AI_MEMORY_GIST_TOKEN` from a secret, `AI_MEMORY_ENABLED` from the presence of both (FR-007, WC-002). No runtime file and the user prompt is not in git; the system prompt template stays a module constant. `.env` accepts a quoted multi-line value for local runs. The model default is `deepseek-v4.1-flash` because `glm-5.3-flash` exhausts the 8000-token budget on reasoning alone for a three-league digest (8000/8000, `content: null`, no prose), while the default completes the same payload in about 2,057 reasoning tokens and 9 seconds; `glm-5.3-flash` remains a supported choice through `AI_SUMMARY_MODEL`, at the cost of a much larger `AI_SUMMARY_MAX_TOKENS` or a `reasoning_effort` the endpoint honours. Enabling the feature needs only a key: the endpoint default matches the model default. A default endpoint we do not control can change upstream, and the failure is visible — notice plus `::warning::` — rather than silent, which is why the default is acceptable now. The default base URL and the model id belong in `.env.example` and the README's configuration section: a plan requirement, not a code comment. Memory has no size knob and no cap: the archive is sent whole (FR-014), and the only reply-side bound is `AI_SUMMARY_MAX_TOKENS`, which governs the reply, not the prompt.

## Data Requirements

### Input

- The weekly report's existing data: `list[DivisionData]`, `list[ChallengeResult]`, `list[WeeklyChallenge] | None`, `current_week`, optional `ChampionshipLeaderboard`, as already assembled in `main.py`.
- The value of `AI_SUMMARY_USER_PROMPT`, if any (FR-010).
- Feature configuration from the table above.
- Phase 1 needs no new input: `DivisionData.games` already carries `team_name`, `score`, `opponent_name`, `opponent_score`, `won`, `week`, `margin` and `division` for every game of the season, and FR-011 is derived from it. The league-wide view (FR-012) needs nothing more: `DivisionData.teams` ranks the standings and `weekly_games` carries the week's matchups.
- Phase 2 adds one input, read at the start of the run: the archive from the gist (FR-013, FR-014).

### Model additions this feature requires

- **No model additions for Phase 1.** `DivisionData.reg_season_count` already exists as `int | None`, populated from the ESPN `League` settings (FR-002's "weeks remaining" reads it, and is `null` when it is unknown), and `GameResult` already carries every field FR-011 derives from, including `score`, `opponent_score` and `week`. The league-wide view is built from `TeamStats` and `WeeklyGameResult` the report already holds, so it adds no model either — only digest keys.
- `AIProvenance` gains `history_weeks: int` (always), plus `memory_read: str`, `memory_write: str` and `memory_weeks: list[int]` (Phase 2 only) — FR-005, FR-008, FR-014. The archive itself needs no model: an entry is the narrative the run already built, serialised. No other model changes.

### Prompt

- The system prompt is a module-level constant in the summary service under `ff_tracker/services/`, so a prompt edit is a single reviewable diff; `prompt_sha` is computed from the instructions only — that constant, the league scope and `AI_SUMMARY_USER_PROMPT` (FR-008). Nothing is read from disk: the archive block is the only prompt content that comes from outside the process, and it comes from the gist on each run.

### Output

- `AI summary` value embedded in the report: headline, per-league paragraphs and bullets, season note, provenance (FR-004, FR-005, FR-008).
- On failure: a notice string rendered in the report and, in JSON, `ai_summary.error`.

## Acceptance Criteria

Tested offline with a fake client that records requests and returns canned responses.

- **AC-001** Feature off: zero calls recorded. Each of the five formats is compared against the feature-on output produced in the same test: JSON documents are parsed and compared after removing the `ai_summary` key; console, sheets, email and markdown are compared on everything outside the new block, by asserting the output equals its pre-section prefix followed by its post-section suffix.
- **AC-002** Feature on with a valid fake response: the section appears in all five formats, after the weekly highlights and before the season challenges, labelled AI-generated; JSON `ai_summary` contains headline, one entry per league in digest order, and provenance.
- **AC-003** Multi-league run: exactly one call, regardless of 1, 3 or 10 leagues, and exactly one call in `--output-dir` mode with five formats; the same narrative appears in all five files. With memory on it is still exactly one provider call, plus exactly one store read and at most one store write, for every league count and both output modes.
- **AC-004** Each failure path in FR-006 — HTTP 4xx/5xx, transport error, timeout, `finish_reason=length`, contract mismatch, league-count mismatch — produces: the complete deterministic section set, exit code 0, one notice line in the section's position, no empty heading, no `::warning::` when `GITHUB_ACTIONS` is unset, and exactly one `::warning::` line when it is `true`.
- **AC-005** A fake error body never appears in stdout, stderr, the notice, the warning, or any file written to `--output-dir`; the API key and the gist token appear nowhere, including in any message the store client builds; and the configured endpoint appears, if at all, as its host only — never its path or query.
- **AC-006** At default verbosity, a three-league run emits no API key, gist token, team name, owner name, league ID, memory text, request body, response body or system prompt. A `-vv` run emits the system prompt — the template, the league scope, the user-prompt block when one is set, and, with memory on, the archive block as per-entry week tags only — and still none of the prohibited items: no key, no token, no team or owner name, no league ID, no stored prose, no request or response body; a unique marker planted in the digest never appears. Existing logging in modules this feature does not touch is out of scope.
- **AC-007** `finish_reason: "length"` with complete, parseable content is still treated as FR-006's truncation failure — the content is not rendered.
- **AC-008** League matching follows FR-004's total order: (i) entries reordered, or differing only in case and surrounding whitespace, map by name; (ii) with equal counts and no full name match — including one stray entry or one duplicated entry — every section renders by position under our own league names, and no response-supplied league name appears as a heading; (iii) with differing counts and no full name match, the FR-006 contract failure is reported with the count-mismatch reason and nothing is rendered.

- **AC-011** A paragraph containing a tab, newline, `"`, `<`, `&` and emoji renders as one sheet row and one console line, is HTML-escaped in email, and does not break TSV column counts.
- **AC-012** Edge-case inputs — single league, a league with no matchups this week, Week 15 playoff mode, Week 17 championship mode, and a digest with no player data — each produce a valid request and a rendered section; the digest sent in Weeks 15–16 carries bracket matchups and the 7 player highlights, and in Week 17 the championship leaderboard, matching what the formatters display; the mode the digest derives agrees with the mode each of the five formatters renders for the same inputs.

- **AC-025** A league with no games sends `"history": null` and the run still renders; a league with exactly one week sends one `weeks_included` entry, a streak of length 1, and `scoring_trend: null` for every team in it; the block is present in regular, playoff and championship fixtures; each of those three runs makes exactly one provider call, and the test asserts no other outbound call was made.

## Edge Cases

1. **Provider returns well-formed JSON for the wrong week or season** — shape and league matching pass; there is no further verification (see Not doing). The report's deterministic sections remain the source of truth.
2. **Very long prose** — normalised to the FR-004 caps before render, then flattened to one TSV row; a single unbroken token wider than a table cell is still truncated by that format, as it is for any cell.
3. **A week with no completed games** — Week 1 before kickoff, or a run whose week could not be detected: `history` is `null`, the prompt says so, and no seasonal pattern may be cited (FR-011, FR-004). Memory is unaffected; a run with no usable week cannot key a new entry, so it writes nothing and records `skipped` (FR-014).

## Constitution Deviations

**Article III (Fail-Fast Error Handling).** This feature violates the "no partial data tolerance" clause on purpose: an AI narrative failure degrades the report instead of failing it. Reasoning: the narrative is cosmetic, the report carries the league's weekly facts, and the report runs on a weekly schedule where a failed proxy, model retirement or HTTP 410 would otherwise deny the league its report entirely. The exception is bounded — it applies only to obtaining, matching and normalising the narrative, and to the memory cases in FR-014 (a read failure never appears in the report and is silent unless it is an authentication failure, and a write failure warns and ships). ESPN data failures, configuration errors (including an oversized `AI_SUMMARY_USER_PROMPT`, a missing key and a missing gist id or token) and every other failure path still fail fast. Omitting the section is never silent — notice plus Actions warning — and no memory outcome is unrecorded: `provenance.memory_read`, `provenance.memory_write` and `provenance.memory_weeks` carry them into the archived JSON. Length normalisation never fails the run: the contract already requires at least one non-empty paragraph per league, and normalisation only drops or shortens content, so the report always ships. This exemption must be recorded in the plan's Complexity Tracking.

**Articles III and V, "no retry logic" — one bounded exception.** FR-003 allows a single retry, and only for a contract failure: malformed JSON, a wrong shape, a league-count or name mismatch, or an empty required field. It exists because that class of failure is sampling noise rather than a statement about the provider; it never repeats an HTTP error, a transport error, a timeout or a truncation; the retry reuses the same request object, so prompt, model and budget are unchanged; and a second contract failure is the ordinary notice. It is existing behaviour, not something this amendment adds, but the constitution requires every non-compliance to be documented, so it is recorded here.

**Article V (External API Respect).** The memory store is a second external API, so the same discipline applies: at most one read and one write per run regardless of league count, no retries of its own, and the client is one-shot like the provider client. It adds two round-trips to a run that already makes one provider call, and nothing about it changes ESPN traffic: both phases read data the report has already fetched, and Phase 1 makes no network call at all.

**Article X (Performance).** The 5-second typical run applies to the deterministic report with the feature off. With the feature on, the run additionally waits for provider latency (7.7–34.4 s per call in the spike), bounded by `AI_SUMMARY_TIMEOUT` on each socket read. There is no wall-clock deadline, so a pathologically slow provider can exceed it. Phase 1 adds no request — the history block is computed in-process from games already loaded — and Phase 2 adds at most two store round-trips, each bounded by the same per-socket-read timeout. Callers that care about schedule duration leave the feature off.

## Out of Scope (Not doing)

- The season recap (`ff-season-recap`) and championship (`ff-championship`) CLIs.
- Anthropic, Gemini or any provider API family other than OpenAI-compatible Chat Completions; provider SDKs.
- Streaming, caching, and any retry beyond FR-003's single contract-only attempt — including a second attempt with a fallback model.
- A second provider call, a second model or streaming for memory: the entry is the narrative the one call already returned (FR-003, FR-014).
- A user-authored system prompt: the template itself is a module constant, and only the `AI_SUMMARY_USER_PROMPT` suffix is configurable. Configuration cannot override the contract or the caps.
- Adding `weekly_games` to the JSON formatter (the digest is the AI payload, not a new public shape).
- Changing, reordering or reformatting any existing deterministic section.
- Per-format or per-league opt-out: when the feature is on, all five formats get the section.
- Fact-checking the prose beyond the contract, league matching and caps in FR-004, and beyond the user-prompt precedence rule in FR-010 — including anything the user prompt asks it to say.
- Any `--format-arg` for this feature; credentials and provider settings are environment only.
- **Receipts.** The AI commenting on, grading or critiquing its own earlier calls — dropped, not deferred. The owner values league trends and voice continuity; a model reviewing its own output spends prompt budget and prose on material no reader asked for, and it would need a second source of "what was predicted" that this feature deliberately does not keep.
- A hand-written lore file, a repository branch, a second private repository or an external key-value store as the memory store. The store is one secret gist and nothing else (FR-013).
- Rendering history or memory anywhere: no new section, table, column or line in any format, and no per-format variation. Both are prompt input only (FR-005).
- Memory for `ff-championship` or `ff-season-recap`, and any history block for them: the same CLI scope as FR-001.
- A new runtime dependency, a new CLI flag, or a size knob: memory has no caps and no pruning to configure (FR-014).
- **Backfill as a product feature.** Seeding the archive from past weeks is not built; the owner will run a throwaway local script once. One build constraint follows from that: generating a given week's summary and appending it to the archive must be callable outside the CLI, so that script reuses this code instead of forking it.
- **Any prompt-side pruning of stored memory.** No selection, window, truncation, compaction, rollover or cross-season carry-over: the file holds one season and the whole of it goes into the prompt (FR-014).
